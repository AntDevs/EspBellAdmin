EspBellAdmin

Project logic, component responsibilities, runtime flow, and ESP32-S3 hardware references.

Inspected scope: project files in source/ and doc/, including web assets and chip-reference files.
Document status: generated from the repository as inspected on 2026-08-28.
Runtime: MicroPython on ESP32-S3 N16R8 with I2S audio output.

1. Purpose and Runtime Summary

EspBellAdmin is an embedded bell and audio appliance. It stores a target audio file on the ESP32 filesystem, plays it through a PCM5102A-compatible I2S DAC, exposes a browser control panel, and can shut down after a configurable period without HTTP activity.

Configured behavior: boot_mode is music_first, so boot audio completes before networking and the web server are started. The configured web endpoint is HTTPS on port 443.

3. Startup and Lifecycle

  1. Configuration: source/main.py reads JSON after removing full-line // and # comments. Plain configured passwords are converted to ENC: values on first load.
  2. Filesystem: required runtime directories are attempted before playback.
  3. Offline audio: with music_first, hal/boot_player.py calls the synchronous wrapper around play_audio_track(mode='boot').
  4. Network: setup_network() tries station mode for the configured router. Failure activates an access point and starts a DNS redirect thread.
  5. Background tasks: smart timeout and LED loop are scheduled on uasyncio.
  6. Web service: app/server.py registers Microdot routes and starts HTTP or HTTPS using configured certificate and key paths.

Observed limitation: MP3 resume uses an approximate 16,000 file-bytes-per-second model and can seek into a compressed frame. Uploaded browser files are converted to WAV, so the normal UI upload path primarily exercises WAV playback.

5. Web UI and API

Browser application

  • index.html loads app.js.
  • app.js loads login, main, upload, and config views dynamically.
  • Selected MP3/WAV files are decoded in the browser and encoded as PCM WAV before upload.
  • style.css supplies responsive presentation.

Routes

  • Public: /, /www/*, /api/info, /api/get-nonce, /api/logout.
  • Protected: /api/config, /api/play, /api/stop, /upload.
  • Catch-all redirects to the configured AP IP.
  • Intended /api/logs registration is after return app and is unreachable.

6. Authentication and Configuration

SecurityManager creates an 8-byte random nonce, stores it with a TTL, and accepts SHA256(password + nonce). A nonce is deleted before hash comparison, making each token single-use. Password encryption uses AES-128-CBC when ucryptolib is available, with a repeating-key XOR fallback.

config.json controls boot mode, timeouts, repeat and fade behavior, resume position, Wi-Fi/AP values, file limits, HTTPS paths, media paths, and I2S pins. The server updates selected values in place with regular expressions to retain comments.

Security observations: the checked-in configuration contains default plaintext credentials; the browser retains the entered password for the session; authenticated configuration responses include decrypted passwords; and the XOR fallback is not cryptographically secure. Secret contents are intentionally excluded from this document.

9. Risks and Follow-up Checks

  • Confirm whether the board onboard LED is GPIO47 or GPIO48, then set one authoritative value.
  • Move or register the logs route before returning the Microdot app if logs are intended to be exposed.
  • Replace regex/string configuration persistence with structured JSON serialization that escapes strings and preserves boolean types.
  • Revisit MP3 resume semantics and ensure stop/deinitialization cannot race the active playback task.
  • Review TLS certificate deployment, default credentials, and whether decrypted passwords should ever be returned to the browser.
  • On real hardware, validate GPIO4 relay polarity and the complete power-latch circuit; startup latch implementation is disabled.
